# ecom: AWS Serverless Ecommerce Platform, fetched on demand

The third external fixture, and the first whose pristine sources already fail the gate for real. The project is [aws-samples/aws-serverless-ecommerce-platform](https://github.com/aws-samples/aws-serverless-ecommerce-platform), MIT-0 licensed (Copyright Amazon.com, Inc. or its affiliates), archived by upstream in July 2024, which makes the pin permanently stable: commit `3b9ef36dd3e338c8ab697c2bcb1b672e064e303c`. Its sources are not vendored here: `external.json` names the repository and the pin, the harness clones it into `evals/.cache/repos/` on demand, and every use verifies `git rev-parse HEAD` against the pin. The patch under `patches/` embeds short fragments of two upstream files as diff context, which is why this attribution exists.

This directory holds only what we author:

- `external.json`, the repository URL and pin
- `arch/model.c4`, the overlay copied onto the pinned sources per run
- `patches/orders-reads-warehouse-table.patch`, the one planted violation
- `greenfield/` and `brownfield/`, the two fixture variants, each with its own `fitc4.eval.ts`, `replies.json`, and `expectations.json`

## What the model transcribes

Each of the ten top-level service directories (delivery, delivery-pricing, frontend-api, orders, payment, payment-3p, platform, products, users, warehouse) carries a `metadata.yaml` whose `dependencies:` list IS the declared architecture, and the model transcribes that list and nothing else: seventeen relationships. The transcription is verified mechanically at authoring time by extracting every `dependencies:` entry from the pristine checkout and diffing the edge list against the model's relationships; the diff is empty. The `pipeline/` directory also carries a `metadata.yaml`, but its dependency list is the wildcard `"*"` and it is the CI/CD stack rather than a service, so it stays outside the fixture. Each service owns its own directory, and its `metadata.yaml` stands in for it wherever a fact needs a file, because that is the file the declared architecture lives in.

The same `metadata.yaml` files also carry the actual wiring. The task description for this fixture assumed the SAM templates embed cross-service SSM paths; the files say otherwise, and the files win. A service's `template.yaml` imports values through typed parameters (`AWS::SSM::Parameter::Value<String>`) that carry no path, and the concrete path each parameter reads is bound in the same service's `metadata.yaml` under `parameters:`, in the form `/ecommerce/{Environment}/<target service>/...`. The second path segment names the target service's namespace, so the `parameters:` block is a second, independent statement of the service graph: what the stack actually reads at deploy time, next to the `dependencies:` list of what it says it needs. Extracting both mechanically from the pristine tree yields seventeen wired edges against the seventeen declared ones, agreeing everywhere except twice:

- **orders -> payment is wired but not declared.** orders' `parameters:` bind `PaymentApiArn` and `PaymentApiUrl` into the stack (the template routes them into a Lambda env var and an IAM policy), while its `dependencies:` list names only delivery-pricing, platform, and products. That is genuine drift shipped by upstream at the pin, and the greenfield expectations pin the resulting `missing-relationship` error as a real finding rather than declaring the edge away.
- **warehouse -> users is declared but not wired.** No SSM parameter backs it at this pin, so the scan never observes it; a declared edge without observations is not a finding, mirroring the boutique fixture's unexercised edges.

Two scoping notes. EventBridge is out of scope on purpose: the templates' event rules do reference other services' event namespaces (`source: [ecommerce.orders]` and similar), but `docs/service_to_service.md` deliberately decouples emitters from reactors through the platform bus, and upstream's own `dependencies:` lists do not count reactions, so a model transcribing those lists must not judge them. And payment-3p is a CDK app with no `template.yaml`, the one service that breaks the SAM pattern, so the scan covers nineteen files: ten `metadata.yaml` plus nine `template.yaml`.

## The two variants

**greenfield** runs the pinned sources unmodified. `agentScan` runs in focused one-shot mode over the nineteen files: their contents are embedded in the request, and the ideal reply reports every `dependencies:` entry and every distinct `parameters:` SSM namespace as a `dependency` observation between the services' `metadata.yaml` files, both kinds even where they duplicate each other, with `examined[]` attesting to all nineteen files including the ones contributing no edges. The stock resolver and rules judge the edges exactly as they judge imports. Thirty-three of the thirty-four observations land on declared relationships; the thirty-fourth is upstream's own orders -> payment wiring, and the gate is red by one genuine error.

**brownfield** applies the one patch, which plants an undeclared edge the way this repository actually wires one: `orders/template.yaml` gains a `WarehouseTableName` typed SSM parameter, and `orders/metadata.yaml` binds it under `parameters:` to `/ecommerce/{Environment}/warehouse/table/name`, the parameter warehouse's own template exports, while the `dependencies:` list stays untouched. Verified mechanically: the same extraction over the patched tree yields exactly one extra wired edge. The expectations pin the second `missing-relationship` error next to the genuine upstream one, and that the scan reports the planted edge honestly rather than tidying it away. That is this fixture's point, sharpened by the pristine tree itself: the declared half of a file and its wiring half can disagree, the agent's observations are the gate's only coverage of the wiring half, and a wrong or missing observation changes the findings by construction.
