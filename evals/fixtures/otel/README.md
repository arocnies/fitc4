# otel: the OpenTelemetry Demo, fetched on demand

The fifth external fixture, and the first authored for the near-zero tier from the start: there is no fixture-written oracle prose at all. The project is [open-telemetry/opentelemetry-demo](https://github.com/open-telemetry/opentelemetry-demo) (Apache-2.0), pinned at release 3.0.0, commit `1755859a9de82c2e5e225be68abc401a5ebf2b4f`. Its sources are not vendored here: `external.json` names the repository and the pin, the harness clones it into `evals/.cache/repos/` on demand, and every use verifies `git rev-parse HEAD` against the pin.

This directory holds only what we author:

- `external.json`, the repository URL and pin
- `arch/model.c4`, the overlay copied onto the pinned sources per run
- `greenfield/`, the one variant so far, with its `fitc4.eval.ts`, `replies.json`, and expectations

## Why this repository

The suite's other compose fixture (supabase) is a hosting stack: services and a database. This one is the system-design catalog in one pin: twenty-three services including a cache (`valkey-cart`), a database (`astronomy-db`), a message broker (`kafka`, with `checkout` producing and `accounting` plus `fraud-detection` consuming), a feature-flag daemon (`flagd`) most services consult, an Envoy front proxy, an nginx image server, a load generator, and a telemetry collector every service exports to. The architecture question a stranger would actually ask of fitc4 — what do I get on a stack like this before writing anything — is the question the fixture's two tiers answer.

## What the model transcribes

The graph is the union of `compose.yaml` and the `compose.full.yaml` overlay (the overlay adds the Kafka pipeline), and each file states the architecture twice over:

1. **`depends_on`**: each key of a service's `depends_on` block is one edge.
2. **The address-variable naming convention**: each service-naming environment reference ending in `_ADDR` or `_HOST` — the variable's own KEY, or a `${...}` reference to such a variable inside a value — whose stem names another service declared in these files is one edge. `CART_ADDR` names `cart`, `FLAGD_HOST` names `flagd`, `VALKEY_ADDR` names `valkey-cart` (the one service its stem matches by prefix), and `${OTEL_COLLECTOR_HOST}` inside flagd's exporter endpoint names the collector as surely as frontend's `OTEL_COLLECTOR_HOST` key does. The rule self-scopes: a stem naming no declared service states nothing (`GRAFANA_HOST` and `JAEGER_HOST` address services of overlay files outside this two-file world, `ENVOY_ADDR` names no service at all, and `${POSTGRES_HOST}` resolves to `astronomy-db` only through `.env`, a binding the text never shows), and a self-reference (frontend's own `FRONTEND_ADDR`) is an address, not an edge. This is a fact about the names, not the values: the values live in `.env`, which the scan never sees (the focused listing skips hidden files).

Extracting both mechanically from the pinned tree yields 64 edges, and the model transcribes exactly that union. Thirteen edges are stated by the naming convention alone and by no `depends_on` — `shipping -> quote`, the collector's two scrape targets (`frontend-proxy`, `image-provider`) and its Kafka feed, `telemetry-docs -> otel-collector`, the three `FLAGD_HOST` carriers that never declare a startup dependency on flagd (`email`, `frontend-proxy`, `fraud-detection`), and the three telemetry exports stated only as `${OTEL_COLLECTOR_HOST}` references inside endpoint values (`flagd`, `kafka`, `load-generator`) — so a scan that reads only `depends_on` measurably under-reports the file.

Both halves of that rule were measured in, not assumed, each by a live pass against a narrower answer key scoring an honest reading as an error — which is the fixture being wrong, not the model. The first pass ran with an `_ADDR`-only oracle, and gpt-5.6-luna read email's `FLAGD_HOST` as the true edge it is; the convention is the repository's own and symmetric in both suffixes, so the oracle took the second suffix. The second pass ran with a keys-only oracle that dismissed value interpolations as deployment choices, and luna read flagd's and kafka's `${OTEL_COLLECTOR_HOST}` exporter endpoints as the edges they are; where the name appears makes no difference to what it states, so the oracle took the value references too. The supabase fixture's `${POSTGRES_HOST}` exclusion survives both corrections mechanically: its stem names no declared service, so it needs no special rule here.

Ownership is the repository's own statement too: each service claims the `src/<name>/` directory the `*_DOCKERFILE` variables in `.env` bind to it (`src/postgresql` for `astronomy-db`; the mounted config directories for `flagd` and the collector). `valkey-cart` runs a stock image with no directory at this pin, so it stays a description-only element and is expected to surface as `unobserved-elements`.

## The two tiers

**`otel/greenfield`** (the base row, gated in stub mode) is the `user-hint` tier: 25 words naming the two compose files and the address-variable convention, nothing about what counts as a dependency. The recorded ideal answers in service-name vocabulary (`{ kind: 'service', id: 'checkout' }`), so `source-root`'s element-name resolution — including the spelling-insensitive step that lets `product-catalog` find `productCatalog` — is exercised on every CI run. The expectations pin all 64 observations, all 64 resolved associations, and two findings: the `unobserved-elements` info for `valkey-cart`, and one `circular-dependency` warning for the fixture's most instructive fact — the telemetry loop (every service exports to the collector, the collector scrapes the front proxy, the proxy fronts the frontend) makes one 18-service strongly connected component out of the store. Its pinned witness, `ad -> otel-collector -> frontend-proxy -> frontend -> ad`, is verified edge-by-edge against the extraction; the pinned `related` list is the full membership, deliberately, because the witness printer's own bug (below) showed that a witness can look right while the membership is wrong. A live run that misses member edges will therefore show the pin as a miss beside a near-identical emitted finding — that is the measurement working, not the pin failing.

Tolerated-but-never-required output is enumerated mechanically from the same extraction. `observations.may` carries a `file` observation per focused compose file (the scorer's own canonical example of contract-permitted output), the three self-edges a model may honestly read from a service's own address variable (`frontend`, `kafka`, `otel-collector`), and the ten `unresolved-dependency` abstentions for `_ADDR`/`_HOST` stems that name no declared service (`grafana`, `jaeger`, `postgres`, and friends) — the reply contract blesses exactly that abstention for "a reliance whose target you cannot locate", and staying silent under the oracle's own scoping is equally right, so neither reading may lose the row. `findingsMay` (added to the harness for this fixture) tolerates what those permissions deterministically produce downstream — the `unresolved-import` warnings behind the abstentions, the `unmapped-source` warnings behind the unowned file observations: tolerating an observation while penalizing its consequence would make the `may` a trap.

Authoring that pin found a real bug before any live call: the witness printer used to walk greedily and fabricate its closing edge on any component where the sorted-first walk strands itself, which this SCC's `flagd-ui` spur triggered. The fix (a shortest-cycle BFS) and its regression test live in the package; the fixture keeps the shape that caught it.

**`otel/greenfield@default-prompt`** (the floor, `gate: false`) is the same wiring with zero authored words. This floor's first measurement was the quiet kind: under the pre-2026-08-31 default a live model volunteered the entire dependency graph with `compose.yaml` as every subject — the import contract's "subject is the importing file" collapsing a 23-service topology into a star from one unowned file — so nothing landed on an element, nothing was checked, and the gate was green. That measurement went into the tool as the shipped default's declaration branch (the declaring component is the subject, never the declaring file), and the re-snapshotted floor is what the branch buys with zero authored words: all 51 `depends_on` edges reported in service vocabulary, all 51 resolving onto declared relationships, both compose files reported and honestly warned as unowned. What zero words still cannot buy is the repository's naming convention — the 13 `_ADDR`/`_HOST` edges, the telemetry loop they close, and the `circular-dependency` finding with them remain the hint tier's measured value, which is now exactly the distance between owner knowledge and tool defaults, rather than between working and not working. What a live model volunteers beyond the floor prints as `floor(drift)`.
