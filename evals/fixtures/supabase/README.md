# supabase: the self-hosting stack, fetched on demand

The fourth external fixture, and the reason fragment claims exist: eleven services whose entire declared architecture lives in one file. The project is [supabase/supabase](https://github.com/supabase/supabase), Apache-2.0 licensed (Copyright Supabase Inc.), pinned at commit `7b04fc7d09b97ef68357c0bd7f172da05c9af58f` and scoped to its `docker/` directory, the self-hosting compose stack. The repository is a multi-gigabyte monorepo, so this is also the first fixture to use the manifest's `sparse` field: the harness clones bloblessly with `--no-checkout`, limits the work tree to `docker/` with `git sparse-checkout set`, and only then checks out the pin, materializing tens of megabytes instead of gigabytes. Every use still verifies `git rev-parse HEAD` against the pin. The patch under `patches/` embeds a short fragment of the upstream compose file as diff context, which is why this attribution exists.

This directory holds only what we author:

- `external.json`, the repository URL, the pin, and the sparse paths
- `arch/model.c4`, the overlay copied onto the pinned sources per run
- `patches/auth-email-hook-to-functions.patch`, the one planted violation
- `greenfield/`, `brownfield/`, and `draft/`, the three fixture variants, each with its own eval spec, `replies.json`, and `expectations.json`

## What the model transcribes

`docker/docker-compose.yml` declares the whole stack at this pin: eleven services (studio, api-gw, auth, rest, realtime, storage, imgproxy, meta, functions, db, supavisor). The compose file states its architecture explicitly, twice over: `depends_on` blocks order startup against the services a container needs, and environment URLs wire services to each other by literal hostname (`STUDIO_PG_META_URL: http://meta:8080`). The model transcribes the union of both statements and nothing else, twelve relationships: ten `depends_on` edges plus two environment-URL edges (`studio -> meta` and `studio -> api-gw`) that no `depends_on` restates. Three more environment URLs restate `depends_on` edges (`storage -> rest`, `storage -> imgproxy`, `functions -> api-gw`), so the scan reports fifteen dependency observations over the twelve declared edges.

The transcription is verified mechanically at authoring time by extracting both statements from the pinned file and diffing the union against the model's relationships; the diff is empty. The oracle, reproducible over the file's disciplined two-space indentation with no YAML library:

1. Service names are the 2-space-indented keys inside the top-level `services:` block.
2. `depends_on` edges are the 6-space-indented keys inside a service's `depends_on:` block (this file uses the long, condition-carrying form throughout).
3. Environment-URL edges are `environment:` values containing `scheme://host`, keeping only hosts that literally name another service declared in the same file, one edge per distinct target per service.

Two scoping notes, both places where the files overruled this fixture's initial premises. First, the pin has eleven services, not the thirteen the classic stack is known for: Envoy replaced Kong as the default API gateway (the compose service is `api-gw`, aliased to both `envoy` and `kong` on the network, with Kong itself moved to the `docker-compose.kong.yml` overlay), and the analytics pair (logflare, vector) moved to the `docker-compose.logs.yml` overlay. The overlay compose files are out of scope; the fixture transcribes `docker-compose.yml` alone. Second, database URLs assembled from `${POSTGRES_HOST}` are not edges: the variable exists so the stack can run against an external Postgres, so its host is a deployment choice rather than a literal service reference. Every `db` edge in the model comes from `depends_on`. The one consequence worth naming: studio and functions read the database only through `${POSTGRES_HOST}` variables and declare no `depends_on: db`, so a strictly literal oracle records no `studio -> db` or `functions -> db` edge, and the model declares none. One genuine upstream curiosity is declared as the file states it: the gateway health-gates on studio (`api-gw -> studio`) while studio's `SUPABASE_URL` points back through the gateway (`studio -> api-gw`), a mutual pair both directions of which the file says out loud.

## Ownership design note

This fixture was built as the deliberate stress test for sub-file ownership, and it earned its point. The first attempt followed the earlier fixtures' precedent: find a per-service file or directory to stand in for each service, as boutique used `src/<name>/` build directories and ecom used each service's own `metadata.yaml`. At this pin that precedent has nothing to grab: `docker/volumes/` holds directories for the gateway config (`api`), `db`, `functions`, `logs`, `pooler`, `proxy`, and `snippets`, and nothing at all for auth, rest, realtime, meta, imgproxy, studio, or even storage (its mount target is created at runtime and is not checked in). At most four of the eleven services could claim an honest per-service directory. The alternatives were invented overlay stand-in files, which would ground the model in files upstream does not have, or one blanket claim over `docker/`, under which every service edge resolves inside a single element's boundary and every wrong or missing agent observation is consequence-free. Both fail the gate-consequence principle, so the fixture is built on the fragment-locator mechanism instead: each element claims `sources 'docker/docker-compose.yml#services.<name>'`, the scan emits subjects of the same form, and resolution is the ordinary longest-claim rule with the fragment's dots guarding boundaries the way directory prefixes' trailing slashes do. A fragment claim nothing observes inside the examined file is an `unmatched-sources` error, so even a silently omitted service changes the deterministic findings. See the fragment-claims section of [docs/DESIGN.md](../../../docs/DESIGN.md) for the mechanism.

## The three variants

**greenfield** runs the pinned compose file unmodified. `agentScan` runs in focused one-shot mode over the single file, embedded whole (21336 bytes at the pin), and the ideal reply reports all fifteen dependency observations between fragment locators, with `examined[]` attesting to the file. The stock resolver and rules judge the fragment edges exactly as they judge imports, every one resolves onto a declared relationship, and the gate is green with zero findings.

**brownfield** applies the one patch: the auth service's send-email hook, shipped commented out by upstream with an external example host, is enabled and pointed at the in-stack edge-functions service (`GOTRUE_HOOK_SEND_EMAIL_URI: "http://functions:9000/email_sender"`), written exactly the way every literal service-host URL in this file is written. Verified mechanically: the same oracle over the patched file yields exactly one extra edge, `auth -> functions`. The expectations pin the resulting `missing-relationship` error and that the scan reports the planted edge honestly rather than tidying it away. Both endpoints of the plant live in the same file, which is this fixture's sharpest version of the usual point: only per-service fragment ownership makes the wrong edge land between two different elements, where the deterministic rules can see it.

**draft** runs `fitc4 draft` over the unmodified pin instead of the gate, and is the end-to-end proof of fragment-derived draft elements: eleven elements drafted from one file. The scan is the gate variants' focused `agentScan` with one added instruction, emit one `file` observation per service fragment locator (`docker/docker-compose.yml#services.<name>`), the same rule a real user drafting from this config would write. Draft turns each distinct observed fragment into its own element claiming the locator verbatim, nested under a container element for the compose file, and resolves the fifteen dependency observations onto the fragment elements by the ordinary longest-claim rule, twelve distinct drift-tagged edges. The recorded ideal reply is the greenfield reply plus the eleven file observations, and `draft/expectations.json` restates the gate model's eleven services and twelve oracle edges as draft references, matched by sources claim, here the fragment locator. The deterministic stub scorecard: `draft-edges 12 hits, 0 misses, 0 extras` and `draft-elements 11 hits, 0 misses, 1 extra`, the one extra being the pinned container element for the compose file itself, scaffolding the reference has no counterpart for.
